## 1. Идея

**SystemPulse** — коробочная система для разработчиков: подключаешь Java-сервис, разворачиваешь комплект контейнеров и получаешь сбор ошибок, их приоритизацию и оповещения, а в перспективе — анализ инцидентов и метрик.

Пока подключён один тестовый сервис, который иногда выдаёт ошибки. Сам проект также будет полигоном для практики с **Codex и агентной разработкой**.

Развёртывание — **Docker Swarm**. Kubernetes можно рассмотреть позднее, если появится необходимость.

## 2. Архитектура
```
Подключённый Java-сервис
  SLF4J → Logback Appender → сейчас: синхронный HTTP-запрос на событие
                           → позже: Kafka
                                      │
                                      ▼
                         SystemPulse: Java 26 / Spring Boot
                           ├─ PostgreSQL — события, правила,
                           │  приоритеты и состояние обработки
                           ├─ консольные оповещения
                           └─ позже: Elasticsearch, Telegram, LLM

Хост и контейнеры
  Node Exporter + cAdvisor → Prometheus → Grafana

PostgreSQL подключённого сервиса
  → отдельный сбор статистики и проблем запросов
```

**Сейчас в основе:** Java 26, Spring Boot, PostgreSQL, Docker Swarm, Prometheus, Node Exporter, cAdvisor и Grafana.

**Позже:** Elasticsearch для поиска, Telegram для оповещений, Kafka заменит HTTP-приём логов и будет использоваться для внутренней обработки, LLM для анализа. MinIO сейчас не нужен. Redis не нужен для хранения метрик — для них есть Prometheus.

## 3. Сбор логов

Для подключённого приложения будет Spring Boot Starter с **Logback Appender**. Он перехватывает обычные вызовы SLF4J — например, `log.error(...)`; менять существующие уровни логирования и бизнес-код не требуется.

Appender передаёт событие в SystemPulse **синхронно, по одному HTTP-запросу на событие**. В библиотеке — минимальная подготовка события и отправка, без определения приоритета, анализа и группировки. Kafka и буферизация в библиотеке сейчас не нужны.

HTTP-передача временная. Позже от неё отказываемся в пользу Kafka: приложение будет публиковать события в Kafka, а SystemPulse — читать их из топика. Это уменьшит риск потери логов при недоступности SystemPulse и позволит надёжнее управлять повторной доставкой.

Событие содержит:

- время, уровень лога, имя logger’а и сообщение;
- класс исключения, цепочку причин и stack trace, если они есть;
- имя сервиса, окружение и версию;
- `traceId` или `errorCode` из MDC, если приложение их передало.

Синхронный сетевой вызов может задержать поток, который записывает лог. Поэтому позже нужно будет определить таймаут и поведение при недоступности SystemPulse. Режим отправки при этом остаётся синхронным.

Логи приложения и системные данные — разные источники: Logback Appender собирает события Java-приложения; логи ОС и контейнеров требуют отдельного сбора.

## 4. Приоритеты и правила

Уровень лога — не бизнес-приоритет: `ERROR` сам по себе не означает P1.

В PostgreSQL будут:

- справочник приоритетов с кодами вроде `P1`, `P2` и их порядком важности;
- отдельная таблица правил, сопоставляющих известную ошибку с приоритетом;
- отдельная настройка, нужно ли по этому правилу оповещать.

Например, в правилах можно указать:

text

```
PaymentGatewayUnavailableException → P1, оповещать
PaymentRejectedException           → P4, не оповещать
```

Правила могут учитывать класс исключения, `errorCode` и сервис. Ключевые слова в тексте сообщения не используем как основной способ классификации. Если правила пересекутся, порядок их приоритета ещё надо будет определить.

### YAML-конфигурация

Правила будут в отдельном файле — например, `systempulse-rules.yml`, подключённом из основного конфига приложения.

При синхронизации с PostgreSQL:

- правило из YAML создаётся или обновляется по стабильному ID;
- правило, которого нет в YAML, **не удаляется** из базы;
- явный `removed` деактивирует правило;
- физически данные не удаляются.

Так конфигурация остаётся отдельной от основного файла, а история событий не теряет информацию о правилах.

## 5. Приём и обработка событий

При поступлении события SystemPulse сначала быстро проверяет известные критические правила — **до записи в общий поток необработанных событий**.

- **Совпало с P1:** событие идёт по срочному пути; SystemPulse сохраняет его и сразу оповещает, не дожидаясь пакетной обработки или Elasticsearch.
- **P1 не найден:** событие сохраняется как сырое, ещё не классифицированное; позднее оно обрабатывается отдельно, в том числе пачками.

«До сохранения» здесь означает до обычного пути сохранения необработанных логов. Критическое событие не должно пропасть: оно тоже фиксируется, просто идёт по срочному пути.

Пока не решено, хранить ли события обоих путей в одной таблице или в разных. Логические потоки отличаются, физическую структуру таблиц выберем позже.

## 6. Неизвестные ошибки и оповещения

Если ни одно правило не совпало, система знает только, что ошибка **не классифицирована**. Это не доказывает ни её низкую, ни высокую бизнес-критичность.

Поэтому неизвестную ошибку нельзя автоматически назначать P1 или другому бизнес-приоритету. Она остаётся `UNCLASSIFIED`, сохраняется, а разработчик сможет изучить её и добавить правило. В будущем алгоритм или LLM могут предложить классификацию, но не назначать критичность без подтверждения.

Первоначально выводим оповещения в консоль. Для распознанных ошибок приоритет и необходимость оповещения берём из правил. Политику вывода неизвестных ошибок отдельно определим позже.

## 7. События, инциденты и связь с падениями

В первой версии главное — **собирать события и оповещать о них**. Сложная группировка ошибок разных сервисов в один инцидент откладывается.

Позднее инцидент сможет объединять связанные ошибки из нескольких сервисов, например возникшие в ходе одного запроса или процесса. Надёжнее всего связывать их по общему `traceId` или `correlationId`. Одного совпадения по времени недостаточно, чтобы утверждать, что ошибки причинно связаны.

При отчёте об инциденте можно будет добавлять состояние контейнера и метрик около времени ошибки:

- что происходило за выбранный интервал **до и после** события;
- загрузка CPU, память и сетевой трафик;
- состояние контейнера, его перезапуски и код выхода;
- связанные логи.

Источником временных метрик останется Prometheus; в данных инцидента можно хранить временное окно и ссылки на связанные наблюдения.

Для связи ошибок с падением сервиса одного Appender недостаточно. Он увидит исключения, которые приложение записало через логирование, но не гарантирует перехват всех необработанных исключений и фатальных ошибок JVM. Позднее для этого потребуется учитывать также stdout/stderr контейнера, события Docker, код выхода, перезапуски, OOM и доступные JVM crash-логи.

## 8. Метрики контейнеров

Метрики привязываем к хосту и контейнерам:

- **Node Exporter** — метрики хоста;
- **cAdvisor** — метрики контейнеров, включая CPU, память и принятый/отправленный сетевой трафик;
- **Prometheus** — хранение временных рядов;
- **Grafana** — графики и дашборды.

Метрики не храним в Redis или PostgreSQL.

## 9. PostgreSQL подключённого сервиса

Отдельно от базы SystemPulse можно собирать состояние PostgreSQL самого подключённого сервиса:

- долгие транзакции, `idle in transaction`, блокировки и ожидания — например, через `pg_stat_activity`;
- статистику нормализованных запросов — через `pg_stat_statements`, если он включён;
- dead tuples и состояние autovacuum;
- deadlocks.

Это разные явления: `idle in transaction` — открытая транзакция без активного запроса; dead tuples — старые версии строк, которые PostgreSQL ещё не убрал; deadlock — взаимная блокировка транзакций.

Для сбора нужен пользователь с ограниченными правами. Конкретный способ сбора и представления этих данных пока не выбран.

## 10. Хранение и транзакции

PostgreSQL — основное хранилище событий, правил и состояния обработки. **Elasticsearch отложен**: позднее его можно подключить как поисковый индекс, а не как замену основной базе.

Транзакции нужны, когда обработка события меняет несколько связанных записей. Например, вместе фиксируются классификация события, обновление инцидента и намерение отправить оповещение. Если одна из записей не удалась, не должны остаться частично обновлённые данные.

Внешний вызов — например, отправку в будущий Telegram или Elasticsearch — нельзя сделать частью транзакции PostgreSQL. Позднее такие действия можно будет надёжно выполнять после коммита через outbox. Сейчас достаточно не усложнять модель транзакциями ради самих транзакций.

## 11. Отчёты, LLM и Codex

Позднее SystemPulse сможет формировать отчёты: сколько было P1/P2 за месяц, какие сервисы затронуты и как показатели изменились. Важно будет отдельно считать количество **событий** и количество **инцидентов**.

LLM сможет суммировать контекст инцидента: связанные логи, метрики и состояние контейнеров — со ссылками на источники. Она не выполняет команды; неизвестную критичность без подтверждения не назначает.

Codex и агентная разработка — цель работы **над проектом**, но пока не часть архитектуры продукта. Как именно делить задачи между тобой и агентом, решим после твоего разговора со знакомым.

## 12. Что пока открыто

Не решаем сегодня:

- одна таблица событий или раздельное хранение срочного и обычного потоков;
- точные правила группировки и связывания ошибок разных сервисов;
- сроки и детали перехода Appender с HTTP на Kafka;
- конкретная реализация сбора статистики PostgreSQL;
- сроки хранения логов и политика оповещения о неизвестных ошибках.

**Зафиксировано главное:** название **SystemPulse**; Java 26/Spring Boot; Swarm; временный синхронный HTTP-отправитель через Logback Appender с последующим переходом на Kafka; быстрый путь для известных P1; сырые остальные события с последующей обработкой; PostgreSQL; метрики контейнеров через Prometheus/Grafana. Elasticsearch, Telegram, Kafka, LLM и сложная межсервисная корреляция — позже.
