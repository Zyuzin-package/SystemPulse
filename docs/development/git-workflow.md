# Git workflow

## Ветки и версии

Схема работы:

`task#001 → develop → main + тег версии`

- `main` — основная ветка с проверенными выпусками. Прямые рабочие коммиты в неё запрещены.
- `develop` — ветка текущей разработки. В неё попадают завершённые задачи.
- `task#NNN` — отдельная ветка для одной задачи, например `task#001`. Она создаётся от актуальной `develop`. Номера назначаются последовательно и не используются повторно.
- Если ветки `develop` ещё нет, сначала создай её от `main`.

Версии выпусков отмечаются тегами, а не отдельными ветками. Например, `v0.1.0` — тег конкретного проверенного состояния проекта.

Формат версии: `vMAJOR.MINOR.PATCH`.

- `MAJOR` увеличивается при несовместимых изменениях.
- `MINOR` — при добавлении новой функциональности.
- `PATCH` — при исправлении ошибок без изменения прежнего поведения.
- `v0.0.0` — тег начального состояния, а не ветка. Первый функциональный выпуск можно отметить тегом `v0.1.0`.
- Версия меняется только при выпуске, а не после каждой задачи или каждого коммита.

## Перед работой

- Проверь текущую ветку и `git status`.
- Если есть незакоммиченные изменения, не удаляй, не прячь и не включай их в задачу автоматически. Приостанови работу и спроси, что с ними делать.
- Создавай ветку задачи от актуальной `develop`.
- Если проект синхронизируется с удалённым репозиторием, перед началом работы обнови `develop` до актуального состояния.

## Во время работы

- Одна ветка — одна задача. Не смешивай с ней несвязанные изменения.
- В коммит добавляй только файлы, относящиеся к задаче.

## Коммиты

- Коммить только после прямого указания.
- Формат сообщения: `<тип>: <краткое описание>`.
- Основные типы: `feat`, `fix`, `test`, `docs`, `build`, `refactor`.
- Примеры: `feat: add console alert formatter`, `docs: add git workflow`.

## Слияние

- После проверки задачи её ветка сливается в `develop`.
- Выпуск создаётся из проверенного состояния `develop`: `main` перемещается на соответствующий коммит через fast-forward.
- Fast-forward не создаёт новый коммит в `main`: ветка `main` начинает указывать на уже существующий проверенный коммит из `develop`. Поэтому прямых рабочих коммитов в `main` по-прежнему нет.
- На этот коммит ставится тег выпуска, например `v0.1.0`.
- После слияния задачи проверь, что изменения находятся в `develop`. После выпуска проверь, что `main` указывает на коммит с тегом версии.
- Никогда не удаляй никакие ветки.

## Завершение задачи

- После успешного коммита отправь ветку задачи на удалённый сервер.
- Переключись на `develop`, обнови её fast-forward из удалённого репозитория и слей проверенную ветку задачи через fast-forward.
- Отправь обновлённую `develop` на удалённый сервер и оставайся на ней.

## Безопасность

- Не используй команды, которые удаляют или принудительно переписывают изменения, например `reset --hard`, `clean -fd` или force push, без прямого разрешения.
- При конфликте слияния не выбирай нужную версию молча: покажи конфликт и уточни решение.

## Работа Codex

- По умолчанию Codex изучает Git-состояние, меняет файлы и запускает проверки.
- Коммит выполняется только по прямой просьбе.
- После успешного коммита Codex завершает задачу по правилам раздела «Завершение задачи».
- Удаление веток выполняет пользователь или Codex по прямой просьбе.
